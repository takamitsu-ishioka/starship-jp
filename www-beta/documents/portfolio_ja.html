エクスリンクさんは元々ショートメッセージ一括送信システムを持っていましたが、そのシステムには次のような問題がありました。
  1. jsmpp（Java の SMPP ライブラリ）に頼り切った高速化不能の送信モジュール
    1. Java 製 ORマッパー Hibernate がすべての DB テーブルをロックしてしまうためマルチプロセス化不能、そのため、
      1. それがボトルネックとなってスループットが低いところで頭打ちになり
      2. また、単一障害点となってしばしばシステム障害を引き起こしていた。
  2. PHP で HTML を生成するタイプの、アーキテクチャも見た目も古い管理画面 GUI。
  3. 公開 API が php で実装されていたため、リクエストのたびに DB を検索せざるを得ず、スループットが低い。
  4. 継続的な開発と運用の仕組みもツールも存在せず、すべてをプログラマーの手作業と注意力のみに依存していたため、しばしば障害が発生。
  5. Java の宿命である GC によるスループットの異常な低下が定期的に発生。そのたびにプログラマー（私ではありません）が手動で送信系プロセスを再起動。
  6. DB のログのレコード数が多くなるとスループットが低下。そのたびにプログラマーが手動で DB テーブルのレコードを削除
私はそれらの問題を解決するために、全てを概念設計からやり直し、全く新しく実装しました。
  1. 送信モジュールを高速化
    1. C++ で生の SMPP 通信プロトコルを実装。1 SMPP アカウント 1 プロセスでマルチプロセス化し、submit_sm, deliver_sm の送受信処理を並列化。
      このアーキテクチャならば、SMPP の契約数とプロセス数（必要なら仮想マシン数）を増やせば、ほぼそれに比例してスループットが大きくなるので、今後もいくらでも拡張可能です（ボトルネックは DB のみ。これについては問題解消の腹案あり）。
    2. 処理済みの DB レコードは別のテーブルに移動するようにしました。
    3. それらにより、スループットは旧システムの 10 倍になりました。
  2. 管理画面を ajax モデルで一新。
    1. サーバーは HTML の動的生成を行わず、スタティックな HTML と javascript を返すだけ。
    2. サーバーは API コマンドを処理する。API コマンドの中身はほぼ DBMS との通信と結果の加工と JSON 化。生の php（フレームワーク無し）で実装。
    3. クライアントは jquery, bootstrap と某モダンなテンプレートで実装。
    4. ドラッグできるダイアログ、D&D で行の順序を変えられる表、問題の箇所に表示されるトゲ付き吹き出し風ツールチップ等、既成の部品の挙動がイマイチだったものは自作。
  3. 公開 API を C++ で実装。DB のデータをメモリにキャッシュすることでスループットを数十倍にしました。
  4. 管理画面と送信モジュールのシステムをそれぞれ「開発用」「商用β」「商用」の 3 系統作成。それらの間の差分表示、dry run モードでの更新、実際の更新を行う bash スクリプトを作成。
    今はこの体制のことを CI/CD (Continuous Integration and Continuous Delivery) と呼ぶようですが、当時はあまり意識されない概念だったような気がします。
  5. 以上を実現するために DB のテーブル定義を全て新たに設計。旧システムから新システムの DB に一括変換するスクリプトを作成。
    つまり、旧システムから流用したのは顧客のデータだけです。
役割 以上の作業を、送信モジュールと公開 API と DB については設計から実装、テストまで私一人で実行。
GUI と内部 API も大枠は私が作り、generic.html および php の function Generic($args) を作成して他のプログラマーに使ってもらうようにしました。
枠の中身をデバッグし充実させることと、新機能を加えることは他の人たちに手伝ってもらいました。
