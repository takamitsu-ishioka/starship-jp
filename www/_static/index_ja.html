職務経歴4 - ショートメッセージ一括大量送信

株式会社エクスリンクのショートメッセージ一括大量送信システムの開発
2010～2022
AWS
Linux (Amazon Linux, Amazon Linux 2)
Apache, RDS (PostgreSQL), Aurora (PostgreSQL)
C++ (gcc), HTML, css, javascript, jquery, bootstrap, PHP, bash, Java
（2010～2014 は同社で動画配信サービスや音声合成 Web API サーバーや動画・音声を合成するキャンペーンサイト構築等の作業をいくつかしましたが、細かい受託開発なので割愛します）

エクスリンクさんは元々ショートメッセージ一括送信システムを持っていましたが、そのシステムには次のような問題がありました。

  1. jsmpp（Java の SMPP ライブラリ）に頼り切った高速化不能の送信モジュール
    Java 製 ORマッパー Hibernate がすべての DB テーブルをロックしてしまうためマルチプロセス化不能、そのため、
    1. それがボトルネックとなってスループットが低いところで頭打ちになり
    2. また、単一障害点となってしばしばシステム障害を引き起こしていた
  2. サーバーサイド (php) で HTML を動的に生成するタイプの、アーキテクチャも見た目も古い管理画面 GUI
  3. 公開 API が php で実装されていたため、リクエストのたびに DB を検索せざるを得ず、スループットが低い
  4. 継続的な開発と運用の仕組みもツールも存在せず、すべてをプログラマーの手作業と注意力のみに依存していたため、しばしば障害が発生
  5. Java の宿命である GC によるスループットの異常な低下が定期的に発生。そのたびにプログラマーが手動で送信系プロセスを再起動
  6. DB の送信ログのレコード数が多くなるとスループットが低下。そのたびにプログラマーが手動で DB テーブルのレコードを削除

私はそれらの問題を解決するために、全てを概念設計からやり直し、全く新しく実装しました。

  1. 送信モジュールを高速化
    1. C++ で生の SMPP 通信プロトコルを実装
      1 SMPP アカウント 1 プロセスでマルチプロセス化し、submit_sm, deliver_sm の送受信処理を並列化
    2. 処理済みの DB レコードは別のテーブルに移動
    それらにより、スループットは旧システムの 10 倍になりました。
    また、定期的なスループットの低下もなくなりました。
    このアーキテクチャならば、SMPP の契約数とプロセス数（必要なら仮想マシン数）を増やせば、ほぼそれに比例してスループットが大きくなるので、今後もいくらでも拡張可能です（ボトルネックは DB のみ。これについてはデータベース・サーバーのスペックを上げずにボトルネックを解消する案があります）。
  2. 管理画面を ajax モデルで一新
    1. サーバースクリプト (php) は HTML の動的生成を行わず、スタティックな HTML と javascript を返すだけ
      ただし、#include による画面要素の部品化は行う
    2. サーバーは API コマンドを処理する。API コマンドの中身はほぼ DBMS との通信と結果の加工と JSON 化
      生の php（フレームワーク無し）で実装
    3. クライアントは生の javascript と、jquery, bootstrap と某モダンなテンプレートで実装
    4. draggable ダイアログ、D&D で列の順序を変えられる表、問題の箇所に表示されるトゲ付きnoty 風ツールチップ、モダンなドロップダウンリスト等、既成の部品の挙動がイマイチだったものは自作
  3. 公開 API を C++ で実装。DB のデータをメモリにキャッシュすることでスループットを数十倍に
  4. 管理画面と送信モジュールのシステムをそれぞれ「開発用」「商用β」「商用」の 3 系統作成
  5. それらの間の差分表示、dry run モードでの更新ファイル確認、実際の更新を行う bash スクリプトを作成
    今はこの体制のことを CI/CD (Continuous Integration and Continuous Delivery) と呼ぶようですが、当時は（少なくとも日本では）あまり意識されない概念だったような気がします
  6. 以上を実現するために DB のテーブル定義を全て新たに設計
    旧システムから新システムの DB に一括変換するスクリプトを作成
    つまり、旧システムから流用したのは顧客のデータだけです
以上の作業を、DB と送信モジュールと公開 API については設計から実装、テストまで私一人で実行
GUI と内部 API も大枠は私が作り、generic.html および php の function Generic($args) を作成して他のプログラマーに使ってもらうようにしました
枠の中身をデバッグし充実させることと、新機能を追加することは他の人たちに手伝ってもらいました

      4. サポートセンター機能

      1. x-www-form-urlencodedでリクエストを受け取り、多くの場合 DB クエリを発行し、結果を JSON 形式で返す

      1. TCPDetective から x-www-form-urlencoded でリクエストを受け取り、DB にログを書き込み、結果を JSON 形式で返す

このウェブサイトの特徴
  1. クッキーをまったく使わない。従って当然、「疑似セッション」の仕組みも使っていないので、LB での特別な配慮が不要、また、セッションのタイムアウトも無い
  2. ユーザー認証は API 呼び出しのたびに毎回行う
  3. まったくページ遷移をしない、いわゆる SPA (Single Page Application) のフレームワーク（自作）を使用
    1. そのおかげで「状態遷移」をクライアントのメモリ上で行うことができる
      つまり、ウェブアプリでありながら、昔からある PC やスマホのアプリケーションと同じ造りになった
      そのため、見かけのページがどんなに変わっても、ユーザー情報や加工中の中間的データをそのページで使用することができる
      これによりウェブアプリの特殊性が消え、非常にプログラムが書きやすくなった
    2. サーバー側で HTML の動的生成をまったく行わないので、サーバー側のフレームワークもスクリプトも必要としない。当然、「テンプレート」も無い
      サーバー側にはただ静的な html ファイルと javascript があるだけ
    3. サイトを構成するページ群の HTML の内部構造に関して、クライアントはまったく何の想定もしない。どんな構造の HTML でも表示可能
      そのため、デザイナーさんが作成した「サーバーサイドスクリプトを想定しないただの HTML」をそのまま使用することができる
    4. このフレームワークは、/index.html と /js/common.js と /js/website.js によって実現されている。ライブラリは jquery
      要求されたページの html を $.ajax() で取得し、取得した html の中に
      <!-- __INCLUDE__ /foobar.html -->
      という「スロット」があれば、その html を再帰的に取得し、取得した html の文字列でそのスロットを置換する
      特殊な記法も、jquery 以外のライブラリの知識も不要
  4. クライアント（管理画面）、内部 API、データベース、公開 API、TCPDetective ビルド環境、tarball ビルドデーモンのセットが、「開発」「商用β」「商用」の 3 セット作成してある（ただしデータベースは「商用β」と「商用」が同じもの）
    それらの間の差分表示、--dry-run モードによる更新ファイルのリスト表示、実際の更新を行う bash スクリプト

「手持ちの道具を組み合わせてできることをやる」
のではなく
「まず目的を定め、それを実現するために何が必要かを考える」
そして
『無いものは作る』


そして、能書きを垂れるだけではなく、実装の過程で未知の技術が必要になれば、それをその場で習得しつつ、実際に動くものを作る力があります。


必要な技術はすべて必要性を感じてから習得してきたので、GCP、TypeScript、Python、機械学習等、今後必要になる未経験の技術も短期間で使いこなす自信があります。
例: 今、GCP で TensorFlow2 を使ってみています（既に理解したつもりになっています）。
例: 先週、Codecademy で TypeScript のコースを始めました（既に理解したつもりになっています）。
例: ChatGPT-4 は既に手放せない日常のツールになっています。この経歴書も ChatGPT と相談しながら書きました。


必要に応じて中～小規模のライブラリやフレームワークなら自分で作ることができます。
