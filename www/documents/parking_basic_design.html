API は生の PHP で実装（フレームワークは使わない）。コマンドに対応する関数（例えば Create******()）を呼び出す。 ・内部 API 関数（例えば Create******()）は生の SQL クエリーで DB テーブルを操作し、結果を JSON 形式で返す。 ・DB は Multi-AZ の RDS を直接使う。「サーバーレス」などの抽象化技術は使わない（高価な上に細かい調整がしにくいから）。 ・返された JSON 形式のデータを $.ajax() のコールバック関数が受け取り、画面に反映する。 ・以上の構造を持つ EC2 (Amazon Linux 2) インスタンスを、とりあえず 2 台作成し、ELB にぶら下げる。 ・以上の構造を持つウェブアプリを「開発」「商用β」「商用」の 3 セット作成する（EC2, ELB は共用）。 ・たいていのウェブアプリでは開発環境と商用環境の構造が大きく違っているので、「商用環境でしか再現しないエラー」が発生すると詰む。が、この構造ならば開発環境と商用環境が全く同じなので、その種のエラーは発生しない。 ・次の機能を持つ bash スクリプトを作成する（注：このスクリプトは作成済み）。 ・「開発」と「商用β」、「商用β」と「商用」のスクリプトや .htaccess などのファイルの差分を表示する。 ・同じく、どのファイルが更新されているかを表示する。 ・同じく、更新されているファイルをコピーする。 ※この 10 年ほどの間に石岡が作ったウェブアプリは全部この構造です。つまり、実現可能性もパフォーマンスも検証済み。 実際、例えば https://www.tcpdetective.com/ の GUI のスクリプトと API のスクリプトと DNS 設定と Apache 設定をまるごとコピーしてドメイン名だけ書き換えれば、骨組みは完成です。あとは DB の中身、内部 API の関数、GUI の HTML と javascript を書き換えれば出来上がり。 ※この構造は「コンテナ」や「サーバーレス」などの余計な抽象化フレームワークを使わないので安上がり（一桁安い）だし細かい調整が自由自在にできます。 また、時間がたつと必ず発生する、「あれこれのフレームワークやライブラリや言語のバージョンが合わない」問題も少なくて済みます。 結果としてテスト、デバッグ、機能拡張が、非常にやりやすくなります。 ・将来の機能拡張のご提案 ・オーナーのログイン、ユーザー登録機能を追加 ・https://www.tcpdetective.com/
