From 2010 to 2014, I worked on several projects at the company, such as a video distribution service, a speech synthesis Web API server, and a campaign site that combines videos and audio, but I will omit the details as these were small contracted development projects.

EXLINK originally had a mass SMS sending system, but it had the following problems:
  1. The transmission module depended entirely on jsmpp (Java's SMPP library), making it impossible to speed up. Java ORM Hibernate locked all DB tables, preventing multiprocessing, which:
    1. Acted as a bottleneck, limiting the throughput, and
    2. Also served as a single point of failure, often causing system failures.
  2. An old-fashioned management GUI that dynamically generated HTML on the server side (php).
  3. The public API was implemented in PHP, requiring a DB search for each request, resulting in low throughput.
  4. No system or tools for continuous development and operation, leading to frequent failures as everything depended on the programmer's manual work and attention.
  5. Periodic significant drops in throughput due to Java's inevitable GC.
  6. As the number of DB transmission log records increased, throughput decreased.

To solve these problems, I started from conceptual design and re-implemented everything:
  1. Speeded up the transmission module:
    1. Implemented the raw SMPP communication protocol in C++ (with socket + pthread), multiprocessed by one SMPP account per process, and parallelized the send/receive process of submit_sm and deliver_sm.
    2. Moved processed DB records to a different table.
    As a result, the throughput became 10 times that of the old system, and periodic drops in throughput were eliminated. With this architecture, the throughput can be increased almost proportionally by increasing the number of SMPP contracts, processes, and if necessary, the number of virtual machines. The only bottleneck is the DB, for which I have a plan to eliminate without having to increase the specs of the database server.
  2. Completely renewed the Admin Console with the ajax model:
    1. The server script (php) does not dynamically generate HTML, but only returns static HTML and javascript. However, #include is used for screen element components.
    2. The server processes API commands, which mostly consist of communication with the DBMS, processing results, and converting to JSON. This was implemented in raw php (no framework).
    3. The client was implemented with raw javascript, jquery, bootstrap, and a modern template.
    4. I created components such as draggable dialogs, tables that allow changing the order of columns with D&D, spike-tipped noty-like tooltips that are displayed at problem points, and modern drop-down lists where the behavior of existing components was not satisfactory.
  3. Implemented the public API in C++, caching DB data in memory to improve throughput by several tens of times.
  4. Created three systems for the Admin Console and transmission module: "Development", "Commercial Beta", and "Commercial".
  5. Created bash scripts to display differences between them, confirm update files in dry run mode, and actually update them. Now this system is called CI/CD (Continuous Integration and Continuous Delivery), but at that time, it was not a well-recognized concept, at least in Japan.
  6. Redesigned all DB table definitions to achieve the above, and created scripts to convert from the old system to the new system DB in bulk. In other words, the only data I brought from the old system were customer data.
I did all the work for the DB, transmission module, and public API, from design to implementation and testing by myself.
For the GUI and internal API, I created the overall framework and developed generic.html and the php function Generic($args) for other programmers to use.
I asked others to help debug and enhance the content of the framework and add new features.

Features of this website
  1. It doesn't use cookies at all. Therefore, naturally, it doesn't use the 'pseudo-session' mechanism, so no special considerations are required for load balancing, and there's no session timeout.
  2. User authentication is performed every time an API call is made.
  3. It uses a custom SPA (Single Page Application) framework that doesn't do any page transitions at all.
    1. Thanks to this, 'state transitions' can be performed in client memory.
      In other words, despite being a web application, it is built like traditional PC or smartphone applications.
      Therefore, no matter how much the appearance of the page changes, user information and intermediate data being processed can be used on that page.
      This eliminates the peculiarities of web applications, making programming much easier.
    2. Because it doesn't do any dynamic HTML generation on the server-side, there's no need for server-side frameworks or scripts. Naturally, there are no 'templates'.
      The server-side just has static HTML files and JavaScript.
    3. With regard to the internal structure of the HTML of the pages that make up the site, the client doesn't make any assumptions at all. It can display HTML of any structure.
      Therefore, you can use 'just HTML that doesn't anticipate server-side scripts', created by a designer, as it is.
    4. This framework is realized by /index.html, /js/common.js, and /js/website.js. The library used is jQuery.
      It gets the HTML of the requested page with $.ajax(), and if there's a 'slot' like
      <!-- __INCLUDE__ /foobar.html -->
      in the obtained HTML, it recursively gets that HTML and replaces the slot with the string of the obtained HTML.
      There's no need for special syntax or knowledge of libraries other than jQuery.
  4. Sets of the client (Admin Console), internal API, database, public API, TCPDetective build environment, tarball build daemon have been created for 'development', 'commercial beta', and 'commercial' (although the 'commercial beta' and 'commercial' share the same database).
    There's a bash script to display differences between them, list update files in --dry-run mode, and perform actual updates.
All of planning, designing, implementing, testing, and operating.
